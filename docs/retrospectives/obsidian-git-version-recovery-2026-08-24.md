## Obsidian 笔记旧版本回写与 Git 恢复复盘

`第6讲 数理统计.md` 在同步后与 2026-08-23 提交完全一致、与 2026-08-24 11:55 提交不一致；先备份工作区，再用指定 commit 单文件恢复，最终验证文件与今天 11:55 的版本完全一致。现有证据支持“旧的本地修改在拉取后被重新应用或由编辑器再次写盘”，其中 `git pull --rebase --autostash` 是高概率触发机制，但因缺少当次 pull 日志，不能把它写成唯一已证实根因。

              │

              │
              │ 备份 + 单文件定点恢复

### 为什么空 stash 不能排除 autostash

`git pull --rebase --autostash` 的目标是在工作区不干净时临时保存修改，完成 rebase 后再自动应用。若重新应用成功，临时 stash 通常会被删除，因此事后执行 `git stash list` 可能为空。

这次排障中，最初把“stash 为空”理解为“autostash 没有参与”是不严谨的。正确判断方式是组合证据：

1. 拉取命令是否启用了 `--autostash`。
2. 拉取前工作区是否存在修改。
3. 拉取日志是否包含创建、应用 autostash 的信息。
4. 拉取后工作区内容与哪个 commit 完全一致。
5. 编辑器是否可能持有旧缓冲并在 Git 更新后再次写盘。

缺少第 3 项日志时，应把机制写成高概率判断，而不是唯一根因。

## 并发知识点：编辑器、定时任务与 Git 的竞态

### 它是什么

这里的并发不是多线程计算，而是多个独立执行者在相近时间操作同一份文件：

- Obsidian 负责自动保存编辑缓冲。
- Windows 定时任务负责运行 Git 拉取。
- 每日备份任务负责提交和推送。
- 用户可能同时在终端执行 Git 命令。

这些执行者没有共享锁，也没有统一的版本前置条件，因此会形成竞态条件。

### 为什么本次重要

Git 更新磁盘文件后，如果 Obsidian 仍持有旧缓冲并再次保存，磁盘就可能重新出现旧内容。类似地，autostash 会把拉取前的本地差异重新应用到拉取后的新基线；它保护了“本地修改不丢”，却不能判断该修改是最新编辑还是过期状态。

### 如何验证

| 检查 | 目的 |
|---|---|
| 拉取前后记录 `git status --short` | 确认工作区是否干净 |
| 保存 pull 完整日志和退出码 | 识别 autostash、冲突和失败 |
| 对关键文件比较 commit | 判断文件来自哪个版本 |
| 记录文件修改时间 | 辅助判断是否在 pull 后被编辑器写盘 |
| 关闭 Obsidian 后重放一次 | 隔离编辑器并发写入 |

### 常见失败模式

1. 定时任务在 Obsidian 编辑期间自动拉取。
2. 备份任务把多个未审核文件一次性提交。
3. 拉取成功，但 autostash 把旧差异重新应用。
4. rebase 成功，但编辑器随后保存旧缓冲。
5. 只检查命令退出码，不验证目标文件内容。

### 更安全的自动同步策略

无人值守的知识库拉取不应默认使用 `--autostash`。更安全的策略是：

1. `git fetch` 只下载远端对象，不直接改工作区。
2. 检查 `git status --porcelain`；工作区不干净时停止并记录文件列表。
3. 工作区干净时才执行 `git merge --ff-only` 或等价快进。
4. 拉取后验证关键文件和目标 commit。
5. 将“本地修改如何处理”留给用户显式决定。

这种策略牺牲了无人值守情况下的自动完成率，换来更低的静默覆盖风险。

## Git rebase 与 autostash 知识点

### rebase 是什么

rebase 会把本地提交暂时取下，将分支基线移动到新的上游提交，再把本地提交依次重放。它处理的是提交历史，不等同于简单覆盖文件。

```text
变基前：A---B---C 远端
         \
          D---E 本地

变基后：A---B---C---D'---E'
```

`D'`、`E'` 内容可与原提交相近，但 commit SHA 会改变。

### `pull --rebase --autostash` 的执行语义

概念上的顺序是：

```text
暂存未提交修改
  -> 拉取远端
  -> rebase 本地提交
  -> 重新应用未提交修改
  -> 成功时删除临时 stash
```

它避免了“工作区不干净，无法 rebase”的报错，但也会把拉取前的工作区差异带到新基线上。

### 如何验证 rebase 是否安全完成

```powershell
git -C $repo status
git -C $repo reflog --date=iso -20
git -C $repo log --graph --oneline --decorate -20
git -C $repo diff --check
```

对关键内容还要执行文件级语义验证，而不是只看仓库没有冲突。

### 常见失败模式

| 失败模式 | 表现 | 修法 |
|---|---|---|
| autostash 应用冲突 | 文件有冲突标记，stash 可能保留 | 检查状态，逐文件解决 |
| 旧差异成功应用 | 没有冲突，但内容语义过期 | 与目标 commit 比较，人工选择版本 |
| 编辑器二次写盘 | Git 完成后文件再次变成 `M` | 关闭编辑器重试并查修改时间 |
| rebase 改写本地提交 | 本地 SHA 改变 | 不对共享分支随意 rebase |
| 把 `reset --hard` 当恢复手段 | 所有未提交修改被清除 | 使用单文件、指定 commit 的 restore |

### 什么情况下不应使用

- 共享分支上的提交已被其他人基于其开发时，不应随意 rebase 后强推。
- 无人值守同步且本地目录经常有编辑时，不应默认使用 autostash。
- 无法确认本地修改新旧时，不应自动选择一方内容。
- 只想下载远端信息、不希望修改工作区时，应使用 `git fetch`。

## 工程方法总结

1. **先定边界**：先确认异常属于 Horizon 代码仓库还是 Obsidian vault，避免在错误仓库执行恢复。
2. **先备份再恢复**：恢复前复制当前文件，保证判断错误仍可回退。
3. **用等价性代替目测**：`git diff --quiet <commit> -- <path>` 能证明工作区是否与候选版本完全一致。
4. **最小化修改范围**：使用 `git restore --source=<commit> --worktree -- <path>`，不执行仓库级硬重置。
5. **区分事实与机制**：文件版本、状态和恢复结果是已验证事实；autostash 与编辑器竞态需要日志才能确定唯一触发者。

## 面试回答

### 题目：讲一次你处理数据版本异常的经历

**背景（Situation）**  
一个由 Git 管理的 Obsidian 知识库在自动拉取后，有一篇课程笔记显示为昨天版本。用户担心刚才的拉取回滚了其他笔记。

**任务（Task）**  
需要在不破坏其他未提交笔记的前提下，判断影响范围、找出正确版本、恢复目标文件，并解释自动同步为什么可能出现这种现象。

**行动（Action）**  
我先检查两个仓库的 reflog 和变更范围，排除 Horizon 代码仓库的初始化 reset。随后在 vault 中定位文件路径，通过 `git status` 确认目标文件是工作区修改，再用 `git log --follow` 找到今天和昨天的候选提交。  
我没有直接执行 `reset --hard`，而是先备份当前文件，再分别用 `git diff --quiet` 比较工作区与两个 commit。结果证明工作区与昨天提交完全一致、与今天 11:55 提交不一致。最后使用指定 commit 的单文件 `git restore` 恢复，并再次做完全一致性验证。  
同时，我分析了 rebase、autostash 和 Obsidian 自动保存的并发关系。空 stash 不能排除 autostash，因为成功重放后临时 stash 会自动删除；但由于缺少 pull 原始日志，我把 autostash 标为高概率机制，而没有伪装成唯一已确认根因。

**结果（Result）**  
目标笔记恢复到今天 11:55 的正确版本，验证结果为 `True`；其他本地修改未被覆盖。排障过程进一步沉淀为可重复的单文件恢复流程和更安全的无人值守同步设计。

### 追问：为什么不用 `git reset --hard`？

因为工作区同时还有其他被修改文件。`reset --hard` 会把索引和整个工作区都重置到目标 commit，可能删除用户尚未提交的笔记。指定路径的 `git restore --source=<commit> --worktree -- <path>` 只恢复目标文件，回滚半径最小。

### 追问：rebase 和 merge 的主要区别是什么？

merge 保留分叉并创建合并提交；rebase 把本地提交重放到新的上游基线，使历史更线性，但会改写被重放提交的 SHA。对共享历史应谨慎 rebase，对个人尚未共享的本地提交可用 rebase 整理历史。

### 追问：如何避免再次发生？

定时同步先 `fetch`，再检查工作区是否干净；有修改就停止并告警，干净时只允许 fast-forward。同步期间避免编辑器写盘，结束后验证关键文件与目标 commit。对无法判断新旧的本地差异，不做无人值守自动重放。

## 可读核心要点

|---|---|---|
| 影响范围 | 单文件异常不代表整库回滚 | 先查仓库、状态和变更路径 |
